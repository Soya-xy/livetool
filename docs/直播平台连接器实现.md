# 直播平台连接器实现（链接直播间）

本轮把「连接到直播间」从「仅本地模拟器」扩展为**可用的抖音连接器**，并留出统一的平台接入层。
协议依据见 `C:\Users\Administrator\Desktop\ak\analysis\直播平台链接器实现分析.md`（原版《AKA直播》逆向），
本文记录复刻时的实现方式、实测结论与未确认项。

## 1. 架构

| 文件 | 作用 |
|---|---|
| [connector.go](../connector.go) | 连接器接口、状态机、重连退避、事件归一化、直播间号解析 |
| [connector_douyin.go](../connector_douyin.go) | 抖音连接器（HTTP 拉取线路、房间解析、礼物表、事件映射） |
| [douyin_proto.go](../douyin_proto.go) | 最小 protobuf 解码器（varint / 64 位 / 长度前缀 / 32 位） |
| [connector_douyin_test.go](../connector_douyin_test.go) | 用真实抓包样本回归字段编号与事件映射 |
| [connector_douyin_live_test.go](../connector_douyin_live_test.go) | 联网回归（需显式设置环境变量） |

每个平台实现一个 `liveConnector`：

```go
type liveConnector interface {
    Run(ctx context.Context, sink connectorSink) error
}
```

`Run` 阻塞推送事件，`ctx` 取消立即返回；返回 `nil` 表示正常收尾（主播下播），
返回 `error` 表示失败。连接失败用 `connectorFailure` 区分**可重试**与**致命**：
房间不存在、未开播、平台未实现属于致命错误，直接停在「连接到直播间失败」；
网络错误、风控拒绝、解析失败按 2s 起步、30s 封顶的退避重连，并累加 `reconnects`。

`AppService` 侧的入口仍是原来的两个方法，前端契约不变：

- `ConnConnect(platform, roomID)`：校验平台与卡密 → 解析并保存直播间号 → 置 `connecting` → 异步启动连接器
- `ConnDisconnect()`：取消连接器并等待退出 → 置 `disconnected`

事件经 `enqueueEvent` 进入既有的队列/去重/规则链路，因此弹幕日记、规则触发、
扩展功能都不需要为新平台改代码。

### 连接状态（与原版 `webcastState` 对齐）

| 状态 | 原版取值 | 界面文案 |
|---|---|---|
| `connecting` | connect | 正在连接.. |
| `reconnecting` | reConnect | 重新连接到直播间.. |
| `connected` | success | 已连接到直播间 |
| `error` | error | 连接到直播间失败 |
| `break` | break | 直播间连接断开 |
| `timeout` | timeout | 连接超时 |
| `disconnected` | — | 未连接直播间 |

前端映射在 [frontend/src/shared/connection.ts](../frontend/src/shared/connection.ts)；
侧栏按钮在未连接时是「连接到直播间」、连接中是状态文案并禁用、已连接时是「断开连接」，
底部状态栏与通用设置 A 卡片同步显示状态、重连次数与最近错误。

## 2. 抖音线路

### 2.1 为什么用 `im/fetch` 而不是 `push/v2`

原版抖音有三条线：主线路 / 备用线路 / 浏览器。主线路与备用线路要跑 webmssdk 的 JS 签名
（原版把签名脚本用 goja 执行），浏览器线路要开一个真实 Chromium 让用户扫码登录。

实测（2026-09-24，中国大陆网络）：

| 线路 | 结果 |
|---|---|
| `wss://webcast5-ws-web-lf.douyin.com/webcast/im/push/v2/` 无 Cookie | `Handshake-Msg: http: named cookie not present`（417） |
| 同上，带 `ttwid` | `Handshake-Msg: DEVICE_BLOCKED`（417）→ 说明 WS 线路还需要签名设备指纹 |
| `https://live.douyin.com/webcast/im/fetch/` + `a_bogus=1` | **200，返回 protobuf 增量消息** ✅ |

`im/fetch` 正是原版参数串里 `a_bogus` 为字面占位值 `1` 的那条线（不需要签名），
因此复刻选择它作为抖音的实现，并在设置页说明这一事实。

### 2.2 端点与参数（原版参数串，实测可用）

```text
GET https://live.douyin.com/webcast/im/fetch/
  aid=6383&app_name=douyin_web&live_id=1&device_platform=web&language=zh-CN
  &enter_from=web_live&cookie_enabled=true&screen_width=1920&screen_height=1080
  &browser_language=zh-CN&browser_platform=Win32&browser_name=Mozilla&browser_version=<UA>
  &im_path=/webcast/im/fetch/&identity=audience&room_id=<room_id>
  &resp_content_type=protobuf&version_code=180800&last_rtt=0&did_rule=3&a_bogus=1
  &cursor=<上一轮 cursor>&internal_ext=<上一轮 internal_ext>
Cookie: ttwid=<设备标识，首次访问 live.douyin.com 时自动获取>
```

- `cursor` / `internal_ext` 是增量游标，必须回传，否则重复或丢消息；连接器在每次成功后更新。
- 轮询间隔取服务端响应里的 `fetchInterval`（实测 1000ms），缺省 1s。
- `ttwid` 由连接器自己抓取：访问 `https://live.douyin.com/` 拿 Set-Cookie，无需用户配置。
- `identity` 原版参数串写的是 `author`，实测 `audience` 同样可用，本实现按观众身份取 `audience`。

### 2.3 房间号解析

设置页可填直播间号、直播间链接，或直接粘贴 App 里的分享短链。连接器按顺序处理：

1. **分享短链 / 分享码**（含字母，例如 `85jECCpxkX4`，或 `https://v.douyin.com/85jECCpxkX4/`，或
   「复制打开抖音」的整段分享文本）：请求 `https://v.douyin.com/<码>/` 并读取 302 的 `Location`：

   ```text
   302 → https://webcast.amemv.com/douyin/webcast/reflow/7689131924585270067?iid=...&enable_replay=1
   ```

   路径里的 `/reflow/<room_id>` 就是内部房间号，直接用于拉取线路。
2. **19 位以上的纯数字**：本身即 `room_id`，直接使用。
3. **数字直播间号（web_rid）/ 直播间链接**：访问 `https://live.douyin.com/<web_rid>`，
   从页面 SSR 数据里取内部房间号、主播昵称与在线人数：

   ```text
   "roomId":"7689119271137430281","web_rid":"452111294161","anchor":{"nickname":"..."},"user_count_str":"4000+"
   ```

   未开播时这段是空值，连接器返回「直播间不存在或当前未开播」且不重试。

注意：抖音网页版**不支持用「抖音号」直接进直播间**（`live.douyin.com/<抖音号>` 返回空房间数据），
所以填抖音号会明确提示改用直播间号或分享链接，而不是静默失败。

### 2.5 事件映射

| 抖音消息 | LiveEvent.Kind | 说明 |
|---|---|---|
| `WebcastChatMessage` | `chat` | 文本取 `content` |
| `WebcastGiftMessage` | `gift` | 数量取 `repeat_count`（回退 `combo_count`），名称/图标/价值来自礼物表 |
| `WebcastMemberMessage` | `enter` | 进场 |

## 3. 实测结论与已知限制

**已验证**（2026-09-24，多个真实直播间）：

- 房间解析、ttwid 获取、`im/fetch` 增量拉取、protobuf 解码、礼物表加载均正常。
- 连续观察 40–90 秒可收到弹幕、进场、点赞、关注与在线人数事件；断线后按退避重连。

**限制**：

1. **昵称与用户号被打码**。匿名（未登录）请求下，抖音把 `User.nickname` 下发为「小**」这类掩码、
   `id_str` 固定为 `111111`，与网页版未登录看到的行为一致。按关键词触发的规则不受影响，
   按用户触发的规则在抖音上不可靠。
2. **未观察到礼物消息**。在 6 个直播间（含 10 万+ 在线的大房间）分别观察 40–90 秒，
   `im/fetch` 没有收到 `WebcastGiftMessage`；同一时间用浏览器 hook 观察**官方网页版自己的
   WebSocket**（带真实 `signature`）也没有收到礼物消息。也就是说这不是本实现的缺陷，
   而是抖音对匿名 web 客户端不下发礼物消息。礼物玩法若要覆盖抖音，需要原版那条带签名
   （goja 执行 webmssdk）的 `push/v2` 线路，或改用登录态会话——两者都未验证。
3. **风控**：`im/fetch` 属于原版的「兜底」线路，长时间高频轮询可能被拒绝；
   连接器按服务端下发的间隔请求，并在失败时退避重连。

### 4.1 小红书：协议已摸清，会话获取受阻

本轮用浏览器 hook 抓到了小红书**网页版自己**的 WebSocket 全流程（2026-09-24，房间 `570467490440456288`），
`wss://apppush-rws.xiaohongshu.com/rwp` 是 JSON 文本协议：

```text
1. 认证      t=2, b.d.s=0
   {"v":1,"t":2,"m":"<消息号>","b":{"d":{"a":1,"s":0,"b":{
     "appId":"xhs-pc",
     "authInfo":{"authType":"generic","sid":"a1:<base64>","uid":"<24 位用户号>","domain":"red"},
     "deviceInfo":{"deviceId":...,"fingerprint":...,"platform":"browser","os":"web",...},
     "bizInfos":[{"bizName":"push","serializeType":"json"}],"state":1}}}}
2. 注册业务  t=2, s=1 → b:{"bizInfo":{"bizName":"room","serializeType":"json"},"register":true}
3. 进房      t=2, s=8 → b:{"info":{"bizName":"room","roomId":"<直播间ID>","roomType":"LIVE"}}
4. 心跳      t=3, c="liveHeartBeat", biz="room", b=base64({roomId,roomType,command:1,customData})
5. 推送      t=4 → b.d.b[].d = base64({"command":1,"customData":"<JSON 字符串>","msgId":...,"ts":...})
```

`customData.type` 实测取值：`text`（弹幕）、`audience_join_v2`（进场）、`praise` / `light`（点赞）、
`gift_dock_and_effect` / `gift_settle` / `gift_comment`（礼物）、`fansgroup_join_room_effect`（粉丝团）。
带 `sid` 的连接 45 秒收到 531 帧；**不带 `sid` 时**服务端对 `s=1` / `s=8` 返回
`{"c":3100001,"m":"Account has not privilege"}`。

**卡点**：`sid`（`a1:<base64 protobuf>`，末尾 32 字节签名字段）由
`https://live-room.xiaohongshu.com/api/sns/red/live/web/v1/center/room/join/room` 一类接口签发，
直接请求返回 **406**（需要网页版的 `x-s` 签名头），Go 侧无法自行引导会话。
因此本轮不提供小红书连接器：宁可明确返回「未实现」，也不交付一个连不上的半成品。
后续若要接，可行路径是把网页版放进 WebView2 窗口、用注入脚本转发它自己的 WebSocket 帧
（即原版的「浏览器线路」），代价是要先解决 WebView2 页面到 Go 的数据通道。
